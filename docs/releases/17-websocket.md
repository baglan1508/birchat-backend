# Выпуск 17: realtime по WebSocket

Ветка: `feature/websocket` → `develop` (тест) → `main` (прод)
Пункт плана: №8. Старое приложение не затронуто: опрос сообщений работает как раньше.

## Зачем

Приложение раз в 5 секунд спрашивает сервер о новых сообщениях: задержка до 5 секунд и постоянные запросы от каждого открытого чата. С WebSocket сервер сам присылает событие сразу.

## Что добавлено

* Адрес `/ws`. Вход — первым сообщением `{"type":"auth","accessToken":"…"}` (токен не попадает в адрес и логи). Неверный или истёкший токен — соединение закрывается с кодом `4401`, приложение обновляет токен и подключается заново.
* События участникам чата: `message.created`, `message.deleted`, `chat.read`, `chat.renamed`.
* `{"type":"viewing","chatId":"…"}` от приложения — «чат открыт», push по этому чату не шлётся.
* Сервер шлёт ping каждые 25 секунд, чтобы прокси Render не закрывал молчащее соединение и обрывы обнаруживались.

### Как устроено

* События отправляются в фоне одним потоком (порядок сохраняется), после того как действие сохранено в базе; запрос, вызвавший событие, не ждёт.
* Если никто не подключён, сервер не делает лишних запросов к базе.
* Соединения хранятся в памяти сервера. **Ограничение:** при двух и более серверах событие дойдёт только до подключённых к тому же серверу — тогда нужен общий канал (Postgres LISTEN/NOTIFY или Redis). Сейчас сервер один.
* При деплое соединения рвутся — приложение переподключается и дозапрашивает пропущенное обычными запросами.

Описание для приложения — `docs/flutter-next-build.md`, раздел 5.

## Тесты

* `RealtimeWebSocketHandlerTest`: вход по токену, неверный токен → `4401`, сообщения до входа → `4401`, ping/pong, `viewing` отмечает открытый чат, закрытое соединение забывается.
* `RealtimeEventServiceTest`: событие получают только участники чата; сбой одного соединения не мешает остальным.

## Откат

Rollback деплоя на Render. Приложение без WebSocket продолжит работать через опрос.

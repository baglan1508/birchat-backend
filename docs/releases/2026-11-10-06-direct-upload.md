# Выпуск 06: загрузка файлов напрямую в хранилище и показ фото в приложении

Ветка: `feature/direct-upload` → `develop` (тест) → `main` (прод)
Пункт плана: №6 (см. [README](README.md))

## Проблемы

1. **Файл целиком проходил через сервер.** При загрузке фото или голосового файл до 20 МБ попадал в память backend (512 МБ на всё приложение), а потом отправлялся в Supabase. Несколько одновременных загрузок могли уронить сервер по памяти.
2. **Фото открывалось в браузере телефона**, а не в приложении. Заказчик хочет видеть фото внутри приложения.
3. **Ссылка на каждый файл — отдельный запрос** к backend и к Supabase.

## Что изменилось

### Прямая загрузка (3 шага)

1. `POST /files/upload-url` — backend проверяет права, тип и размер, создаёт запись файла со статусом `PENDING` и выдаёт подписанную ссылку Supabase (действует 2 часа).
2. Телефон загружает файл **прямо в Supabase** по этой ссылке (`PUT`). Backend в передаче данных не участвует.
3. `POST /files/{fileId}/complete` — backend проверяет, что файл лежит в хранилище, берёт **настоящие** размер и тип, переводит файл в `READY`. Подтвердить может только тот, кто загружал.

* Файлы `PENDING` никому не видны: их нет в списке файлов, поиске, ссылках на скачивание, их нельзя отправить в чат.
* Если при подтверждении файл оказался больше 20 МБ — он удаляется из хранилища.
* Недозагруженные файлы старше суток удаляет ночная чистка (из хранилища и из базы).
* Разрешённые типы: `image/*`, `audio/*`, `video/*`, PDF, Word/Excel/PowerPoint, `text/plain`, `text/csv`, ZIP.

### Показ внутри приложения

* `POST /files/download-urls` — подписанные ссылки сразу на много файлов (до 100) **одним запросом** к Supabase. Файлы без доступа не возвращаются.
* Сам показ — на стороне Flutter: картинка грузится по ссылке и показывается в приложении (`CachedNetworkImage`, `photo_view`), голосовые — встроенный плеер. Подробно — [docs/flutter-files.md](../flutter-files.md).

### Прочее

* Запросы к Supabase для подписей, проверок и удаления — с таймаутами (5 с соединение, 15 с ответ).
* Старая загрузка через сервер `POST /files/upload` **пока работает** (текущее приложение не ломается). Отключим после перехода Flutter.

Миграция `V15`: колонка `company_files.status` (`PENDING`/`READY`, существующие файлы — `READY`), индекс для чистки.

Файлы: `SupabaseStorageService`, `CompanyFileService`, `CompanyFileController`, `ChatService`, `CompanyFileRepository`, `CompanyFileEntity`, `DataCleanupService`, `DataCleanupProperties`, новые DTO, `V15__add_company_file_status.sql`, `docs/flutter-files.md`.

## Что это значит для приложения

* Текущее приложение продолжает работать (старая загрузка и `download-url` на месте).
* Новая загрузка и показ фото в приложении — задача Flutter, инструкция и чек-лист: [docs/flutter-files.md](../flutter-files.md).

## Тесты

До этого выпуска тесты **не запускались**: сборка на Render идёт с `-DskipTests`, а CI не было. Теперь GitHub Actions (`.github/workflows/tests.yml`) запускает `mvn test` на каждый PR и push в `develop`/`main`. Первый запуск: **58 тестов, все прошли**.

* `CompanyFileServiceTest`: посторонний не получает ссылку; исполняемые файлы и файлы > 20 МБ отклоняются до загрузки; создаётся файл `PENDING`; подтвердить может только загрузивший; без файла в хранилище подтверждение не проходит; размер и тип берутся из хранилища; слишком большой файл удаляется; пакетные ссылки не возвращают чужие и недозагруженные файлы.
* `DataCleanupServiceTest`: недозагруженные файлы удаляются из хранилища и базы; если хранилище недоступно — запись остаётся.

Деплой `da2f47e` за 1 мин 19 с, миграция V15 применена (бета-база v14 → v15). Проверка через API с настоящим Supabase (bucket `birchat-beta-files`), тестовая компания «E2E тест»:

### Найдено на тесте и исправлено

1. **Слишком большой файл: запись в базе не удалялась.** Удаление записи и ответ `400` были в одной транзакции, и ошибка откатывала удаление. Вреда не было (запись `PENDING` никому не видна, её убрала бы ночная чистка), но задумано было иначе. Исправлено: `completeUpload` — `@Transactional(noRollbackFor = ApiException.class)`.
2. **Неверный запрос давал `500` и ошибку в Sentry.** Неверный метод (например, `GET /api/companies`), несуществующий адрес и битый JSON попадали в общий обработчик. Теперь это `405 METHOD_NOT_ALLOWED`, `404 NOT_FOUND` и `400 BAD_REQUEST`, в Sentry не уходят. Настоящие сбои по-прежнему `500` и в Sentry. Новые коды ошибок: `NOT_FOUND`, `METHOD_NOT_ALLOWED`.
3. **Поле `fileUrl` не открывается** (хранилище закрытое). В [docs/flutter-files.md](../flutter-files.md) добавлено: для показа — только `downloadUrl`.

Тест: `GlobalExceptionHandlerTest` (405, 404, битый JSON → 400, прочее → 500).

Утром проверить: ночная чистка удалила недозагруженный файл `d5a6ba3a-…` (оставлен на тесте специально).

## Откат

Rollback деплоя. Колонка `status` останется, все файлы в ней `READY` — старый код её не читает.

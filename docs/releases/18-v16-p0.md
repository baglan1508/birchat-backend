# Выпуск 18: v1.6 P0 — согласие на AI, приватность сотрудников, удаление сотрудника, алиас `general`

Ветка: `feature/v16-p0` → `develop` (тест) → `main` (прод)
Задачи P0 из `BACKEND_TASKS_v1.6.md` от Flutter-разработчика (0.3, 0.4, 0.5) и замечание из сверки 18.11 про `general`.

## Что изменилось

| Запрос | Кто | Что делает |
|---|---|---|
| `PUT` / `PATCH /api/companies/{companyId}` `{ "aiEnabled": true }` | директор | включает или выключает AI в компании, ответ — `CompanyResponse` |
| `DELETE /api/companies/{companyId}/employees/{userId}` | директор | убирает сотрудника из компании |
| `POST /api/companies/{companyId}/employees` | директор | ответ без `userId` и без профиля человека |
| любой `/chats/general/…` | участник | `general` вместо id общего чата |

### 0.3. Согласие компании на AI

* Новое поле `aiEnabled` в `CompanyResponse` (`/companies/my`, создание компании) и в `company` у `/home`.
* Пока выключено: `/ai/ask` и `/ai/director/summary/today` — `403 AI_DISABLED`, квота не списывается; сводка по расписанию компанию пропускает; новые фото и PDF не уходят модели (помечаются «AI выключен в компании», после включения анализируются только новые файлы — архив модели не отправляется).
* История диалога (`/ai/history`, `/ai/history/clear`) работает и при выключенном AI.
* Миграция `V23`: у существующих компаний `ai_enabled = TRUE` (директора не теряют сводку молча), у новых — `FALSE`.

### 0.4. `POST /employees` не раскрывает чужой профиль

Раньше по номеру телефона директор узнавал, зарегистрирован ли человек в BirChat, как он подписан и его фото.

* Ответ `POST /employees` одинаковый для нового и зарегистрированного номера: `memberId`, имя из запроса, телефон, роль, должность, `status`; `userId` и `avatarUrl` — `null`.
* В списках (`GET /employees`, участники чата) такой сотрудник показывается **под именем, которое ввёл директор**, без фото, пока сам не откроет список компаний (`GET /companies/my`). `userId` в списках есть — по нему директор добавляет человека в группы; у нового и зарегистрированного номера он выглядит одинаково.
* Миграция `V23`: `company_members.invited_name`, `accepted_at`; у всех существующих сотрудников `accepted_at` заполнен — для них ничего не меняется.

### 0.5. Убрать сотрудника

* Только директор (`403 FORBIDDEN`); себя — `400 VALIDATION`; директора — `400 VALIDATION`; не сотрудник — `404 USER_NOT_FOUND`.
* Участие получает статус `REMOVED`; человек выходит из общего чата (он строится по сотрудникам) и из всех групп компании. Сообщения остаются, устройства не трогаем.
* Его запросы к компании дальше — `403 NOT_A_MEMBER`; пуши и события чатов компании ему больше не приходят.
* WebSocket: ему — `{ "type": "company.removed", "companyId" }`, остальным сотрудникам — `{ "type": "member.removed", "companyId", "userId" }`.
* Повторное добавление того же номера возвращает прежнюю запись (раньше упало бы на уникальном ключе `company_id + user_id`).

### Алиас `general`

* Фильтр `GeneralChatAliasFilter` подставляет id общего чата компании в любой путь `/api/companies/{companyId}/chats/general/…`. Старые адреса (`/general/messages`, `/general/read`, `/general/messages/file`) по-прежнему обрабатываются своими методами.
* WebSocket: `{"type":"viewing","chatId":"general","companyId":"…"}` отмечает общий чат открытым. Раньше `general` без UUID игнорировался — и в открытом общем чате приходили пуши.

## Тесты

* `AiServiceTest`: вопрос и сводка при выключенном AI — `AI_DISABLED`, модель не вызывается; посторонний получает `NOT_A_MEMBER` раньше; расписание берёт только компании с согласием.
* `CompanyServiceSettingsTest`: директор включает AI, сотрудник — нет; пустой запрос ничего не меняет; новая компания — AI выключен, директор сразу «зашёл»; список компаний отмечает приглашения принятыми.
* `EmployeeServiceTest`: ответ без `userId` и профиля; ожидающий сотрудник в списке под именем от директора, после входа — под своим; повторное добавление убранного; повторное добавление активного — `409`; удаление: директор, себя нельзя, сотрудник не может, неизвестный — `404`.
* `GeneralChatAliasFilterTest`, `RealtimeWebSocketHandlerTest` (`viewing` с `general`), `RealtimeEventServiceTest` (`company.removed` / `member.removed`).
* CI: миграции V1–V23 на PostgreSQL 18.

## Совместимость

Поля только добавлены. Изменение для старых сборок одно: `userId` в ответе `POST /employees` теперь `null`. Если приложение использует его сразу после добавления (например, чтобы добавить человека в группу), нужно брать `userId` из `GET /employees`.
